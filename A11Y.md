# Accessibility invariants

The Definition of Done points here. Each item is enforceable, and each carries
its source so it can be argued with.

## Enforced in code today

- Text on a color uses `readableForeground()`. It selects by comparing
  contrast ratios, never by thresholding luminance. The `#000`/`#fff` pair
  clears 4.5:1 on every possible color, worst case 4.58:1 at luminance 0.179,
  verified by a sweep of 3,168 combinations across the picker range.
- A caller asking for AAA lands on the scrim branch, which is swept over the
  same 3,168 combinations at 7:1. Its worst background is `#f50000` at
  16.1:1, so the requirement holds with room to spare and `SCRIM_ALPHA` is
  set by how much garment shows through the pill rather than by contrast.
- `contrastOver(fg, bg, alpha)` exists so translucent text can be measured.
  It is how the prototype's `opacity: .8` caption was found to fail, and that
  opacity is not reproduced in the implementation.
- `needsBorder(hex)` decides the hairline on light swatches. This is a
  contrast affordance: without it White, Cream and Light grey vanish into the
  `#d8d5cf` background.
- Color names use OKLab distance rather than RGB. This is the right default
  for perceptual distance on arbitrary camera-read colors, and the name is
  the only non-color channel available to a color-vision-deficient user, so
  naming accuracy matters. It is not a fix for a demonstrated RGB failure: for
  this 18-color palette, the two metrics agree almost everywhere, the
  supposedly confusable warm neutrals sit 37 to 40 RGB units apart, and two
  searches for a case where OKLab beats RGB turned up only near-ties.
  The naming contract only holds near the palette, so `colorName` stops at
  its edge: past `NAME_MAX_DISTANCE` no palette name is claimed, and the
  color is described from its own lightness, chroma and hue instead, as
  "bright green" instead of a confident "Cream". A description deliberately
  carries less than a palette name: a user confirming a camera read can act
  on it, where a wrong name reads as information. Neutrals are exempt,
  because between two neutrals there is no hue to get wrong.
- `jsx-a11y/no-static-element-interactions` and
  `jsx-a11y/interactive-supports-focus` are errors. These are the two rules
  that catch the prototype's unlabeled `<div>` with pointer handlers.
- Hit targets are at least 44 by 44, measured rather than asserted.
  `e2e/invariants.spec.ts` checks the bounding box of every link and button on
  every route in `e2e/routes.ts`. The `touchTarget` token is how a control
  asks for that size, and `44px` appears only in `src/styles/tokens.stylex.ts`,
  but naming the token is not the same as getting the size: a link is inline
  by default and takes a minimum height only once its display allows one.
  This line used to enumerate the controls that used the token, and it was
  wrong — two links were 20 pixels tall while a grep for the token passed.
  The measurement is the invariant; the token is only how it is requested.
- Every route in `e2e/routes.ts` is scanned with axe at WCAG 2.1 AA, checked
  for horizontal overflow at 320px, and checked at 200% text size for content
  that overflows but cannot be scrolled to. The list is the gate: a screen
  added without its route is a screen none of the three checks sees, which is
  why the route goes in with the pull request that creates the screen.
- Focus moves on every screen transition that goes through
  `src/ui/Screen.tsx`, which takes focus to the new screen's `<h1>` after a
  client-side navigation. That is also how the screen is announced: a screen
  reader reads the element it lands on. The move sits on the receiving end
  rather than in a navigate wrapper, because a plain `<Link>` bypasses a
  wrapper. A screen writing its own `<main>` and `<h1>` would still slip past,
  so this is a convention the code makes easy rather than one it enforces.
  What is enforced is that no route escapes the checks: `src/app/routes.test.tsx`
  holds the route table to the list in `e2e/routes.ts`, in both directions.
- The focus move does not fire on first load, where focus belongs at the
  document start, and it does fire on a back navigation to that first entry.
  React Router reports that location's key as `default` both times, which is
  why the guard compares location identity instead. `src/ui/Screen.test.tsx`
  covers both directions; the back case was a real defect, found in review
  after the key comparison shipped.
- `blockLabel(slot, hex)` builds a color block's accessible name, "Top: Pale
  blue". `src/ui/ColorBlock.tsx` puts it on the block's `role="group"` and is
  the function's first caller. `src/ui/ColorBlock.test.tsx` holds it, and also
  holds that a color the palette cannot name is described rather than given a
  confident palette word: on a block, as on a swatch, the name is the only
  non-color channel a color-vision-deficient user has.
- The block's three controls are all `<button>`: the peek strip, the
  alternatives control and the Keep toggle. Each works by keyboard, so every
  destination the block reaches is reachable without a gesture, and swipe and
  long press are additional pointer affordances over them.
  `src/ui/SuggestionBlock.test.tsx` holds it. The backwards swipe is the one
  gesture with no control of its own, and it needs none: the cursor wraps, so
  the previous suggestion is Next pressed `count - 1` times. A Previous button
  would cost a fourth target on a block the product owner sized against thumb
  reach, for a destination Next already reaches.
- A gesture over the block does not also fire the control underneath it. The
  color field is a button covering everything a press can start on, so a
  swipe or a long press would otherwise release into a click and open the
  alternatives sheet on top of what the gesture just did.
  `src/ui/SuggestionBlock.test.tsx` holds both the suppression and the plain
  tap that must survive it.
- Each of the block's controls draws its own focus ring: a `currentColor`
  outline, inset so the block's clipped corners cannot cut it off, plus the
  tint the control shows under a thumb. `currentColor` is what
  `readableForeground` chose for this color, so the ring clears 1.4.11's 3:1
  on any garment color, where the browser default is picked without knowing
  what is underneath it. StyleX emits no CSS under Vitest (ADR 0002) and the
  block has no route yet, so this is the one item here that nothing asserts.
  #17 owes it.
- The long press has a non-gesture alternative. It is the Keep toggle, which
  does the same thing by tap or by keyboard, and the prototype had nothing
  like it. `src/ui/SuggestionBlock.test.tsx` holds it.
- The swipe ignores a gesture where vertical movement dominates, however far
  it travels horizontally. The prototype reads `clientX` and never `clientY`,
  so scrolling the page changed colors under the finger.
  `src/ui/useBlockGestures.test.tsx` holds it.
- The controls' accessible names carry the slot: "Next suggestion for Top",
  "Keep Top", and on the color field "Top, Pale blue, 2 of 5, other options".
  Five blocks share one screen, so the bare strings this file used to record
  would appear five times over and say nothing about which block a button list
  had reached. `src/ui/SuggestionBlock.test.tsx` holds them.
- The field's name is built from the words printed on it, in the order they
  are printed. That is 2.5.3: a Voice Control user saying "click Pale blue"
  has to reach the control that says Pale blue.
  `src/ui/SuggestionBlock.test.tsx` holds it.
- The swipe position indicator has a text equivalent, where the prototype
  conveys position through dot opacity alone. `positionLabel` in
  `src/session/select.ts` formats it, and it goes into the field's accessible
  name rather than only into a span inside the button: an `aria-label`
  replaces a button's contents for naming, so a screen reader reading the
  field would never have reached the span. An unknown position drops out of
  both. `src/ui/SuggestionBlock.test.tsx` asserts the name, not the rendered
  text, because a text query passes whether or not anything can reach the
  text. #17 owes the wiring that supplies the label from the session.

## Owed by later milestones

- Toasts announce through a live region. `src/ui/Announcer.tsx` provides it,
  and the free colour picker is its first consumer: dragging a slider changes
  a colour with no focus move, so the name is announced when it changes. M3's
  toast is wired to the same region in #17.
- Motion durations gate on `prefers-reduced-motion` inside the tokens
  themselves, so a transition that reaches for one cannot forget to opt out.
  `vibrate()` in `src/ui/motion.ts` reads the same query before it calls
  `navigator.vibrate`. Which tokens gate and which must not is held by
  `src/styles/tokens.stylex.test.ts`: the long-press threshold and the two
  toast dwell times deliberately do not, because zeroing an input timing fires
  the press on touch and zeroing a dwell takes the message away before it can
  be read. #17 owes the browser-level check that the shuffle crossfade stops.
- The suggestion block has no route until #17, so Playwright cannot reach it.
  Four checks wait for that screen: the block's computed background against
  the exact hex it was given, the hit-target measurement over its three
  controls, reduced motion asserted in a browser rather than in the token
  source, and the focus ring, whose `currentColor` resolves only once a real
  stylesheet has run. StyleX emits no CSS under Vitest (ADR 0002), so none of
  them can be brought forward.
